# راهنمای انتقال اٌوِرا به PostgreSQL ابری (Neon) و انتقال داده‌های قبلی

این سند دقیقاً مراحل اتصال پروژه به یک دیتابیس **Neon** (یا هر PostgreSQL ابری دیگر مثل Supabase)، ساخت جداول، مقداردهی دسته‌بندی‌ها و **انتقال محصولات سایت قبلی** را قدم‌به‌قدم توضیح می‌دهد.

> **نکته مهم — هیچ داده‌ای حذف نشده است.** تصاویر سایت همگی داخل مخزن هستند
> (`public/assets/img/*.jpg` — بیش از ۱۵۰ فایل) و همراه هر deploy روی Vercel
> منتشر می‌شوند. «نبود محصولات» فقط به این معنی است که دیتابیسی که
> `DATABASE_URL` به آن اشاره می‌کند هنوز خالی است؛ با طی کردن مراحل زیر همه
> دسته‌بندی‌ها و محصولات بازمی‌گردند.

---

## ۱. ساخت دیتابیس در Neon

1. در [neon.tech](https://neon.tech) حساب بسازید و یک **Project** جدید بسازید (Region نزدیک به ایران/اروپا، مثلاً `Frankfurt`).
2. از داشبورد، رشته اتصال را کپی کنید؛ شکلی شبیه زیر دارد:

   ```
   postgresql://USER:PASSWORD@ep-xxxx-xxxx.eu-central-1.aws.neon.tech/neondb?sslmode=require
   ```

3. این رشته را **هرگز** در گیت کامیت نکنید. فقط در Vercel Environment Variables و فایل محلی `.env.local` می‌آید (`.env.local` در `.gitignore` است).

## ۲. تنظیم متغیر محیطی

- **روی سیستم خودتان:** در ریشه پروژه فایل `.env.local` بسازید/ویرایش کنید:

  ```
  DATABASE_URL=postgresql://…?sslmode=require
  NEXT_PUBLIC_SITE_URL=http://localhost:3000
  ```

- **در Vercel:** Project Settings → Environment Variables → کلید `DATABASE_URL` با مقدار Neon (برای Production). `NEXT_PUBLIC_SITE_URL` را هم روی دامنه واقعی (مثلاً `https://overa.vercel.app`) بگذارید تا QR نصب PWA درست ساخته شود.

## ۳. ساخت جداول (Migration — بدون آسیب به داده)

```bash
bunx prisma migrate deploy
```

این دستور فقط migrationهای کنترل‌شده‌ی `prisma/migrations` را اعمال می‌کند و **هرگز داده حذف نمی‌کند**. اجرای دوباره‌اش بی‌خطر است («No pending migrations»).

## ۴. مقداردهی دسته‌بندی‌ها (ضروری برای فرم «ثبت وسیله»)

فرم ثبت وسیله دسته‌بندی‌ها را مستقیم از جدول `Category` می‌خواند؛ در دیتابیس خالی پس «دسته‌بندی‌ها وجود ندارند». با این دستور ۸ دسته‌بندی اصلی ساخته می‌شود — این اسکریپت روی هر دیتابیسی (حتی Production) امن است، فقط-می‌سازد و تکرارش مزجدی نمی‌سازد:

```bash
bun run db:seed:categories
```

## ۵. انتقال محصولات سایت قبلی

### الف) خروجی گرفتن از سیستم قبلی

از سیستم قبلی، فهرست محصولات را به یک فایل JSON با این ساختار خروجی بگیرید (فیلدهای ستاره‌دار اجباری‌اند):

```json
[
  {
    "title": "دوربین سونی A7 IV",
    "category": "digital",
    "brand": "Sony Alpha",
    "description": "توضیح کامل آگهی",
    "specs": "سنسور ۳۳ مگاپیکسل • 4K 60p",
    "dailyPrice": 950000,
    "weeklyPrice": 5100000,
    "deposit": 6000000,
    "city": "تهران",
    "area": "ونک",
    "images": ["75c37134b4d1.jpg", "https://example.com/img.jpg"],
    "status": "ACTIVE"
  }
]
```

- `category` یکی از این‌هاست: `digital`, `home`, `sport`, `tools`, `camping`, `beauty`, `kids`, `other` — یا نام فارسی دقیق همان دسته.
- نام فایل ساده تصویر به‌صورت خودکار به `/assets/img/<name>` تبدیل می‌شود؛ اگر تصویر در سیستم قبلی آدرس اینترنتی داشته، همان URL کامل را بگذارید.

### ب) اجرای import

مالک واقعی آگهی‌ها باید یک حساب واقعی در سایت باشد (اسکریپت عمداً «مالک جعلی» نمی‌سازد). اگر حساب ندارید یک‌بار ثبت‌نام کنید، بعد:

```bash
# اول بدون نوشتن، فقط ببین چه اتفاقی می‌افتد:
bun run db:import --file=./legacy-listings.json --owner-phone=0912XXXXXXX --dry-run=1

# بعد اجرای واقعی (پیش‌فرض ACTIVE؛ برای بررسی ادمین از --status=PENDING استفاده کنید):
bun run db:import --file=./legacy-listings.json --owner-phone=0912XXXXXXX
```

رفتار اسکریپت: فقط-موجودیت‌های جدید می‌سازد، تکراری‌ها (هم‌عنوان + همان مالک) را رد می‌کند، `isDemo=false` ثبت می‌کند تا از محتوای نمایشی جدا بماند، و `searchKey` نرمال‌شده فارسی را برای جستجو می‌سازد.

### ج) اگر خروجی JSON از سیستم قبلی در دسترس نیست

می‌توانید محتوای نمایشی هم‌ارز همان محصولات قبلی را با seed دمو بازسازی کنید (روی دیتابیس ابری عمداً قفل است و باید صریحاً اجازه بدهید):

```bash
OVERA_SEED_ALLOW_REMOTE=1 bun run db:seed
```

این ۱۸ آگهی نمونه (همان تصاویر واقعی مخزن) + حساب‌های نمایشی را می‌سازد؛ همه با `isDemo=true` ثبت می‌شوند تا بعداً قابل تفکیک از محتوای واقعی باشند. **این گزینه برای Production توصیه نمی‌شود** — مسیر درست همان بند «ب» است.

## ۶. تکمیل شاخص جستجو (اگر لازم شد)

اگر داده را با روش دیگری وارد کرده‌اید و جستجو نتیجه نمی‌دهد:

```bash
bun run scripts/backfill-search-keys.ts
```

## ۷. ساخت حساب مدیر پلتفرم

```bash
ADMIN_PHONE=0912XXXXXXX ADMIN_PASSWORD=<رمز-قوی> bun run scripts/create-admin.ts
```

(در deploy با Docker همین متغیرها را به کانتینر بدهید تا entrypoint خودش انجام دهد.)

## ۸. اجرای مجدد seed ها — قانون امنیتی

| اسکریپت                 | روی Neon امن؟                      | رفتار                                          |
| ----------------------- | ---------------------------------- | ---------------------------------------------- |
| `prisma migrate deploy` | بله                                | فقط migrationهای معلق را اعمال می‌کند          |
| `db:seed:categories`    | بله                                | فقط دسته‌بندی‌های ناقص را می‌سازد              |
| `db:import`             | بله                                | فقط آگهی‌های جدید می‌سازد، تکراری را رد می‌کند |
| `db:seed` (دمو)         | فقط با `OVERA_SEED_ALLOW_REMOTE=1` | محتوای نمایشی با `isDemo=true` می‌سازد         |
| `db:reset`              | **خیر — هرگز روی Production**      | دیتابیس را پاک و از نو می‌سازد                 |

هیچ‌کدام از اسکریپت‌های این پروژه عملیات حذف ندارند؛ تنها `db:reset` مخرب است و فقط برای محیط توسعه محلی استفاده می‌شود.

## ۹. تأیید نهایی

1. `bun run dev` → صفحه اصلی باید محصولات را نشان بدهد.
2. `/create-listing` → ۸ دسته‌بندی باید دیده شوند.
3. جستجوی هدر را با یک تکه از نام یک محصول آزمایش کنید (مثلاً «دوربین»).
4. `/api/search?q=لپتاپ` باید JSON واقعی برگرداند.
5. بعد از deploy روی Vercel، همین ۴ آزمایش را روی دامنه اصلی تکرار کنید — داده‌ها بین redeployها ماندگارند چون در Neon ذخیره شده‌اند، نه در سرور اپ.
